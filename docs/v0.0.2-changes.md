# v0.0.2 变更说明与新旧功能对照

- 产品名：**Cross-Workspace Memory**
- 内部包名：`dsh-secure-memory`（保持不变，避免破坏已安装行、客户端模块 id、数据目录和升级路径）
- 版本：`0.0.2`
- 基准：v0.0.1 的 13 项测试全部通过后再修改

---

## 1. 本次修复的真实根因

### 1.1 “新建对话”问题

对 v0.0.1 全量代码扫描：

- 没有 `startSession` / `connectWorkspace` / `openSession`
- 没有 `sessions.fork` / `session.prompt`
- 没有 `window.location =` / `location.href =` / `history.pushState`
- 没有消息提交调用
- Settings iframe 的表单都调用 `preventDefault()`，只做本地 DOM 重绘
- 唯一 `window.prompt` 是删除保险库的 `DELETE` 确认框

**结论：v0.0.1 插件代码中没有创建新会话的路径。**  
因此该现象不可能由这些 UI 状态切换代码直接触发。可能来源是 DSH 宿主对 Settings/路由的自身行为、另一个插件、浏览器扩展或用户点击了其他入口。

v0.0.2 的做法不是“隐藏新会话”，而是：

1. 主功能栏只使用 React 本地 state + 本地 `/secure-memory/api/...` 请求；
2. 不调用任何 DSH 会话创建/fork/prompt/URL/history API；
3. 增加静态回归测试，禁止客户端代码出现这些调用；
4. 在栏中显示当前会话指纹，便于验收“当前会话 ID 不变”；
5. 如果升级后仍出现新会话，需捕获具体点击时刻的 DSH 会话日志/操作者；这不是本插件 UI 的隐藏行为。

### 1.2 重复输入密码问题

根因不是密码验证本身，而是 **Bearer token 只存在于 Settings iframe 的 JS 变量**。切换/刷新 iframe 会丢失 token，于是要求重新输入。

v0.0.2 将 token 提升到 **Client 插件模块闭包**（Dsh 页面运行期），不再写入 iframe 页面变量；主功能栏解锁后，打开 Settings iframe 可通过同源 `postMessage` 接收 token，不需要重复输入。  
**没有保存口令，也没有把 token 写入 localStorage/sessionStorage/cookie。** 整页刷新或 DSH 重启仍需重新解锁。

## 3. 会话级数据模型

新增可选字段（不改变 `STATE_VERSION`）：

```jsonc
{
  "sessionScopes": {
    "session-...": {
      "enabled": true,
      "workspaceIds": ["ws_a", "ws_c"],
      "updatedAt": "2026-11-08T..."
    }
  }
}
```

规则：

- `enabled` 是本次会话总开关。
- `workspaceIds` 只能来自当前有效 grant 的子集；**不能授权**。
- 新会话默认 `enabled=false, workspaceIds=[]`。
- 撤销/过期工作区会从所有会话选择中自动移除。
- 旧 vault 无该字段 → 自动按空对象读取/补字段，不改旧数据。
- v0.0.1 回滚时忽略该字段，不会破坏已有 grants/docs/audit。

## 4. 主功能栏行为

位置：`conversation.input.dock`（输入框上方，full-width list，session scope）。

显示：

- 品牌 **Cross-Workspace Memory**
- 本次会话开关
- 检索状态 pill
- 当前关联工作区数 / 已索引文档数
- 展开/收起
- 锁定/解锁
- 展开后：工作区复选列表、全选/清空、刷新索引、审计/自动锁定说明、最近检索来源、会话指纹

交互全部是 React 局部状态更新：

- 开关 → `POST /session/:id/scope`
- 勾选 → `POST /session/:id/scope`
- 刷新索引 → `POST /session/:id/sync`
- 来源刷新 → 每 3 秒读取 status（Host 对 status 心跳不计入 token/vault idle）
- 不提交用户消息，不创建会话，不改变当前 sessionId。

## 5. 插件冲突检测与降级

已实现（可证实的部分）：

1. **Tool 名称冲突**
   - 注册前 `ctx.tools.get(name)`。
   - 默认保留 `xw_memory_search` / `xw_memory_context` / `xw_memory_status`。
   - 被占用时改用 `cwm_memory_*`（仍冲突则加序号）。
   - 不覆盖其他插件；冲突记录显示在功能栏。
2. **UI slot**
   - 使用唯一 `cwm-main-bar-v2`，避免复用已有 id 替换。
   - `conversation.input.dock` 是 list slot，本身支持多插件共存；不存在“强制覆盖”。
   - 1.5 秒内主 slot 未挂载 → 尝试 `conversation.composer.dock`；仍不可用 → Settings 作为最终入口。
   - 类名统一 `cwm-` 命名空间。
3. **没有注册** DSH 命令、快捷键或全局事件监听，因此没有相应冲突面。
4. **官方限制**：Client `ctx.slots` 只暴露 `register` / `inject` / `registerFactory`，没有公开 occupants 枚举 API。无法可靠读取其他插件占用的 slot、命令、快捷键或事件监听器。v0.0.2 不虚构这些检测结果，只在 Settings/文档中说明限制。

## 6. 安全验证体验

- 首次设置：Settings 内；口令不保存。
- 日常开启/切换：功能栏内；使用页面运行期内存 token，不再每次输入。
- 修改安全设置/撤销/删除：仍需已解锁的管理 token + 明确确认。
- 页面刷新/DSH 重启：token 丢失，需要重新解锁。
- 高风险操作不因“记住”而跳过确认。
- 工作区授权与本次会话关联严格分离：验证身份/解锁不等于自动选中工作区。
